## TL;DR

The multi-tenant **foundation is solid and well-tested** (auth, tenant isolation, the free booking path, migrations, AI copy/imagery). The three things that define the product's ambition are **not there yet**:

1. **Payments don't move money on the live path.** Customers book through the main worker's **no-payment** `/api/bookings`. The advanced Stripe-Connect deposit/checkout engine (`apps/workers/booking`) is **built but orphaned** — not called by the site, and with **no Connect onboarding**, so it can't pay shops or collect the 10% commission the business model (PRD G3) depends on.
2. **Inventory + retail sales don't exist.** Zero catalogue/stock/POS. (Was a PRD Phase-2 *non-goal*; your directive promotes it to a **goal** — recorded here.)
3. **Sites are not unique.** Every shop renders through **one** layout (`CommercialTemplate`); the six "templates" are dead code; ~40% of each page is identical hardcoded copy; and the pipeline generates rich per-shop design intent then discards it. This directly undermines the PRD positioning ("every shop their own fully AI-branded presence").

**Start here:** make the three **P0 decisions** in §3 (they gate everything), then execute the workstreams in §4 in the §6 order. Nothing below has been implemented yet — this is a greenfield remediation from a clean `main`.

- **Lanes** (carried from the prior audit's model):

## 3. P0 decisions required before building

These are **product/architecture decisions** a model cannot make alone. Get an explicit answer (recommended answer given) before the dependent workstreams start.

**D1. Which booking system is canonical?** Two exist and write the same `bookings` table: (A) main worker `/api/bookings` — dynamic slots from `schedules`, no payment, currently LIVE; (B) `apps/workers/booking` — materialised `bw_availability`, Stripe-Connect deposits, tips, QR check-in, POS-style checkout, commission ledger, currently ORPHANED.
→ **Recommended:** promote **(B)** (it already has the payment/POS features the goals need), fold the main worker's public booking into it, and delete the duplicate. If instead deposits are added to (A), then (B) is deleted. **Do not ship both.** Gates WS-1, WS-2, WS-3.

**D2. Payment model = Stripe Connect (confirm).** PRD G3/§5 already specifies "£100 setup + 10% commission via Stripe Connect", and the orphaned worker is built for destination charges. → **Recommended:** confirm Connect (Express) and implement onboarding (WS-2). Alternative (single platform account + manual payouts) contradicts the PRD and is not recommended.

**D3. Money representation.** Everything is `REAL` (float) today. → **Recommended:** migrate to **integer minor units (pence)** system-wide (WS-4) before inventory/COGS multiplies the surface. If deferred, the interim rule is: round every money write to 2dp and centralise on `services/commission.ts` — decide explicitly, do not keep mixing.

Secondary decisions (can be made at each WS): retention period for LEG-6; whether to keep 7 background workers or consolidate; multi-currency now or GBP-only (PRD is UK-first).

## 4. Workstreams

### WS-1 — Reconcile the booking architecture 🔴 sign-off · P0 · effort L
- **Problem:** two divergent booking systems on one `bookings` table; the advanced one is orphaned WIP.
- **Outcome:** exactly one booking system is live end-to-end (per D1), the other deleted; the web app books through it.
- **In scope:** choose + wire one path; migrate/rename availability model; delete the loser; update `$shopSlug.book.tsx` + `booking-staff`/`slots` endpoints; one integration test for the live path.
- **Acceptance:** a customer booking on a seeded shop succeeds through the chosen path; no code references the deleted worker; `bookings` rows have consistent shape; unique-slot race guard (migration `018`) still holds.
- **Key files:** `apps/worker/src/routes/bookings.ts`, `apps/workers/booking/src/**`, `apps/web/app/routes/$shopSlug.book.tsx:59`, `apps/worker/wrangler.toml`.
- **Depends on:** D1. **Blocks:** WS-2, WS-3.
- **Risk:** touching the live booking path; do behind staging E2E.

### WS-2 — Stripe Connect onboarding + payment integrity 🔴 sign-off · P0/P1 · effort L
- **Problem:** nothing populates `stripe_connect_account_id`/`stripe_connect_onboarded`; the whole marketplace payout + commission model is non-functional. Plus latent payment races.
- **Outcome:** shops onboard to Connect (Express), and the chosen booking path takes deposits + captures balances safely.
- **In scope (sequenced):**
  1. Connect account create → `account_links` onboarding UI → `account.updated` webhook that sets the two columns; go-live gate (`booking/setup.ts:42,86`) becomes satisfiable.
  2. **Atomicity:** slot claim via `UPDATE … WHERE is_booked=0` requiring `changes===1` **before** PI creation; checkout via `UPDATE bookings SET status='completed' WHERE status='confirmed'` requiring `changes===1`.
  3. **Idempotency:** deterministic Stripe `Idempotency-Key` on every PI create/capture (`apps/workers/booking/src/lib/stripe.ts`).
  4. **Reconciliation webhook** for booking PaymentIntents (`payment_intent.succeeded`/`charge.refunded`/`charge.dispute.created`) updating `bw_transactions`/`bw_commission_ledger`; keep ledger `pending` until captured (fix "completed before capture").
  5. No-show capture of manual-capture holds (`day.ts:97`).
- **Acceptance:** a test shop completes Connect onboarding; a booking deposit is held then captured; concurrent double-submit does not double-charge (idempotency-key asserted); ledger reflects only captured money; webhook signature verified.
- **Key files:** `apps/workers/booking/src/{routes/bookings.ts,routes/setup.ts,lib/stripe.ts,index.ts}`, new Connect route + webhook, `apps/web` onboarding UI.
- **Depends on:** D1, D2, WS-1. **Related audit items:** §C Critical + High.
- **Risk:** real money; test with Stripe test mode + a dedicated `processed_events` dedup table.

### WS-3 — Inventory + POS subsystem 🟢/🔴 mixed · P0/P1 · effort L (phased)
- **Problem:** Goal #2 has zero implementation; the orphaned checkout can't even represent a counter sale (`bw_booking_items.booking_id NOT NULL`).
- **Outcome:** per-tenant catalogue, stock, and a counter/booking POS that sells services **and** products in one transaction, through **one commerce spine**.
- **Design principle:** reuse `bw_transactions` (tender) + `bw_commission_ledger` (extended with `retail_amount`/`staff_id`); replace `bw_booking_items` with a unified `sale_line_items` + a `sales` header whose `booking_id` is **nullable**. Full recommended schema + phased plan is in **`AUDIT-2026-07-06.md` §D** — implement from there.
- **Phases:** (0) catalogue + stock foundation 🟢; (1) POS core + Stripe checkout + stock decrement 🔴 (money); (2) purchasing/PO + returns + stock-take + back-bar consumption 🟢/🔴; (3) retail commission + reporting (COGS/margin/valuation) + retention 🟢.
- **Acceptance (per phase):** P0 — CRUD a product/variant with SKU, adjust stock via movements, low-stock view; P1 — ring a mixed cart, take payment, stock decrements in the same batch, COGS snapshot recorded; migrations replay clean in the worker test suite.
- **Key files:** new migrations `022+`, `apps/worker/src/db/queries.ts` helpers, new `apps/worker/src/routes/{products,inventory,sales}.ts`, Remix admin screens, R2 image reuse (`staff.ts:177` pattern).
- **Depends on:** D3 (money), ideally WS-1/WS-2 for the shared checkout. **Guardrail:** all DDL in main-worker migrations (canonical owner), never a background-worker `ensure-schema`.

### WS-4 — Money to integer pence 🔴 sign-off · P1 · effort M
- **Problem:** float money across bookings/commission/`bw_*` (and, if unfixed, inventory) → reconciliation drift.
- **Outcome:** money stored as `INTEGER` pence; one rounding path via `services/commission.ts`.
- **In scope:** schema migration converting `REAL`→`INTEGER` with data conversion; update all readers/writers + reporting sums; the booking worker stops bypassing `calculateCommission`.
- **Acceptance:** `SUM()` reports are exact; no float literals in money math; existing tests pass; a migration-replay test covers the conversion.
- **Risk:** prod data migration — back up first (see prior handover), stage it.

### WS-5 — Observability + mandatory CI gate 🟢 autonomous · P1 · effort M
- **Problem:** no error reporting anywhere (no Sentry/`captureException`/`tail_consumers`/`[observability]`); the E2E gate is opt-in via label so most PRs merge with no E2E.
- **Outcome:** prod errors are visible and alertable; a fast smoke E2E runs on **every** PR.
- **In scope:** enable Workers Logs `[observability]` in each `wrangler.toml`; add error reporting + alerting; stop swallowing failures silently in booking/email/queue paths; make a smoke subset mandatory (drop the `e2e` label gate for a fast subset); wire the excluded specs.
- **Acceptance:** a deliberately thrown worker error surfaces in logs/alerts; CI runs the smoke subset unconditionally and is green.
- **Key files:** all `wrangler.toml`, `.github/workflows/e2e.yml`, worker error paths.

### WS-6 — Per-shop uniqueness 🟢/🔴 mixed · P1 · effort M–L
- **Problem:** one live layout; ~40% identical copy; generated design intent discarded.
- **Outcome:** shops are visibly distinct in layout, colour, copy, and imagery.
- **In scope (ordered by ROI):** (1) **stop discarding the spec** — persist + serve `layout_mood`/`brand_voice`/`trust_signals`/`usps`/`hero_cta`/`about_title` + full palette, and replace the hardcoded pillars/steps/CTA/hero-subline 🟢; (2) layout archetypes switched on `layout_mood` 🟢; (3) 5-colour palette tokens + WCAG contrast guard (allow light themes) 🔴 (visual); (4) tokens seeded by `shopId`; (5) curated + self-hosted fonts; (6) optional AI-authored **validated JSON block list** (never raw HTML).
- **Acceptance:** two shops with different `layout_mood`/palette render visibly different structure + colour + copy; no `dangerouslySetInnerHTML` for AI content; a light palette passes AA contrast.
- **Key files:** `apps/web/app/components/CommercialTemplate.tsx`, `CommercialShopChrome.tsx`, `apps/workers/{research,text,builder}/src/**`, migration `021` columns, `$shopSlug._index.tsx`.
- **Cleanup:** delete/repurpose the two dead generation systems (`services/site-generator.ts`, `services/ai-generator.ts`) and the placebo template picker or wire it.

### WS-7 — Public-write abuse surface & residual auth 🔴 sign-off · P1 · effort S–M
- **In scope:** rate-limit + validate + cap `POST /api/waitlist` (also verify shop/service/staff ownership), walk-in join, and the reviews endpoint (require+verify `booking_id`); add KV session-revocation to the booking worker `authMiddleware`; close SEC-3 (email-verified gate on `/api/me`); raise PBKDF2 iterations; add upload size caps; delete the dead `requireShop()`.
- **Acceptance:** abuse endpoints reject floods and cross-tenant data; a revoked token is rejected on the booking worker; `/api/me` requires a verified email.
- **Key files:** `apps/worker/src/routes/{waitlist,walkin,shops}.ts`, `apps/workers/booking/src/middleware/auth.ts`, `dashboard.ts`, `middleware/rbac.ts`.

### WS-8 — Data-layer scale & DR 🔴 sign-off · P1/P2 · effort M
- **In scope:** decide the D1 scaling model (per-tenant/sharded D1, or Durable Objects for hot per-shop booking state) before volume; document D1 backup/point-in-time-recovery; add time-based retention/anonymisation (LEG-6); harden `migrate.mjs` (per-migration transactions instead of benign-error swallowing); make `ensure-schema` files assert-only.
- **Acceptance:** a written DR/backup runbook exists; retention job runs on cron; migration runner wraps each file in a transaction.

## 7. Definition of Done

- 🟢 **Autonomous:** type-check + lint + `npm test` green; new/changed flow exercised by a test or the staging E2E; no silent error-swallowing added; migrations replay clean; PR opened from a branch (never commit straight to `main`).
- 🔴 **Sign-off:** all of the above **plus** a written note of the semantic change (who can do what / what money moves / what prod data changes), tested in Stripe test mode or staging, and **explicit human approval before merge/deploy.** Money and prod-data migrations are backed up first.

## 8. Repo gotchas the next model must know

- **Migrations are the only DDL owner.** `migrate.mjs --remote` is what CI runs; **never `--baseline`** (records without executing → silent gaps); never re-run the operator-only `cleanup-legacy-prod.sql`/`rebuild-bookings-prod.sql` (prod-only, already applied). Background-worker `ensure-schema.ts` files are defensive duplicates only.
- **Remix `.js` route shadowing:** compiled `.js` twins take priority over `.tsx`. Currently there are **none** in `apps/web/app/routes` — keep it that way; regenerate/remove any twin after editing a `.tsx` route.
- **Worker dev proxy is port `8787`;** Remix expects it. Secrets: Pages via `wrangler pages secret put … --project-name pivot-parlor-web`, Worker via `wrangler secret put` (do not cross them).
- **`gh` account silently flips to `jared0565`** — run `gh auth switch --user fbmacagba` before any gh/git op; never push Pivot Parlor to the other account.
- **Staging E2E:** deploy a staging frontend, verify the token is 200 on staging `/auth/me` and 401 on prod **before** any data-creating run; reset `e2e-*` shops first; `--workers=1` (shared staging DB). Full procedure in `docs/runbooks/e2e-staging.md`.
- **UK-first product** (GDPR/PECR, GBP). Product user-facing copy: no em-dashes (`CLAUDE.md`), brand gold `#C9A84C` / dark `#0D0D0D`, Playfair + DM Sans, no blue in marketing.
- **Money is `REAL` everywhere today** — assume float until WS-4 lands; never introduce new `REAL` money columns in WS-3.
