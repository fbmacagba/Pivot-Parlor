# Independent Visual Editor — Design Spec

**Date:** 2026-07-21
**Status:** Approved (brainstorming) — ready for implementation planning

## Goal

Let developers and shop owners edit each site visual — the **logo**, the **hero**, and **each per-service photo** — independently, including uploading the owner's own image to replace any AI-generated one, **without a full destructive site regenerate**. Customised visuals survive a later regenerate.

## Motivation

A full-site regenerate is the only way today to change service imagery, and it overwrites the entire site (copy, design, hero) and drops it to draft. It is also all-or-nothing per image type. Owners frequently have their own photography they want to use. Concretely: FerdyM's Barber Shop currently shows female service photos and the only fix is a destructive regenerate. This facility replaces that with surgical, per-visual editing.

## Locked decisions (from brainstorming)

1. **Surface:** both the developer hub and the shop-admin dashboard, via one shared component. Role-aware.
2. **Actions (role-split):**
   - Shop owner / admin: **upload** own image only.
   - Developer: **upload** + **AI-regenerate that one visual** + **remove**.
3. **Stickiness:** a customised visual (uploaded, or individually set/regenerated by a developer) is **locked** and survives a later full-site regenerate; only still-AI visuals get regenerated.
4. **Architecture:** service-keyed per-service images + light lock flags for hero/logo (see below).

## Non-goals (YAGNI)

- Gallery / signature-section images (only logo, hero, per-service for now).
- Image cropping, editing, or reordering.
- Owner-facing AI regeneration (developer-only by decision).
- The cost optimisation of skipping AI generation for locked visuals during a full regenerate (correctness holds without it; see Regenerate interaction).

## Architecture

### Data model — migration 045

`apps/worker/src/db/migrations/045_visual_editor.sql`:

```sql
ALTER TABLE services   ADD COLUMN image_url TEXT;
ALTER TABLE shop_sites ADD COLUMN locked_images_json TEXT;
```

- `services.image_url` (nullable): a service's own custom photo, keyed by **service ID**. `NULL` → fall back to the AI catalog pool (today's behaviour). Reflected in `schema.sql` (the `services` CREATE TABLE is in the snapshot).
- `shop_sites.locked_images_json` (nullable): a small JSON object marking a custom hero/logo, e.g. `{"hero":true,"logo":true}`. Absent key / falsey → not locked. **Not** reflected in `schema.sql` — `shop_sites` is a migration-only table (created in migration 003, deliberately absent from `schema.sql`).

`schema_migrations` numbering: next migration is **045**; after this, next is 046. The worker test suite replays the full chain and must stay green.

### Custom / locked semantics (derived, no extra bookkeeping)

- A **service** is custom ⟺ `services.image_url IS NOT NULL`.
- The **hero** / **logo** are custom ⟺ their key is present-and-true in `shop_sites.locked_images_json`.
- Setting a visual (upload by owner or dev, or dev AI-regenerate, or dev set) marks it custom/locked. **Remove** (dev only) unmarks it.

### Backend endpoints (`apps/worker/src/routes/shops.ts`)

Extend the existing image endpoints; add one. All are shop-scoped and reuse the existing auth pattern `user.role === "developer" || (user.role === "admin" && user.shop_id === shop.id)`.

1. **`POST /:shopId/upload-image`** (dev or admin-of-shop) — extend `type` from `hero|logo` to also accept `service:<serviceId>`.
   - Validate the service belongs to the shop (`WHERE id = ? AND shop_id = ?`); 404 otherwise.
   - Store the R2 object at the stable key `shops/<slug>/service-<serviceId>.png` (overwrite on re-upload). Return `{ imageUrl }`.
   - Existing validation unchanged: png/jpg/webp, ≤ 5 MB (`MAX_UPLOAD_BYTES`).

2. **`POST /:shopId/save-image`** (dev or admin-of-shop) — extend `type` to `hero|logo|service:<serviceId>`, body `{ type, imageUrl }`.
   - `service:<id>` → `UPDATE services SET image_url = ? WHERE id = ? AND shop_id = ?`.
   - `hero` / `logo` → set `hero_image_url` / `logo_url` (as today) **and** set the corresponding key in `locked_images_json` to `true`.
   - Bust KV `site:<slug>`.

3. **`POST /:shopId/generate-image`** (**developer-only** — add the role check) — extend to `type = service:<serviceId>` (currently hero/logo). Note: this **narrows** the endpoint's current dev-or-admin auth to developer-only, intentionally — owners upload but never AI-regenerate. (No admin UI invokes it today, so no used capability is removed.)
   - Build the service prompt with the same gendered, deterministic template used by the research worker: `Photorealistic close-up of the finished <service name> result on <subject>, flattering professional lighting, square format`, where `<subject>` derives from `shop.type` (`barber_shop` → "a male client", `beauty_parlor` → "a female client", `both` → "a client"). **Extract this template + subject helper into `@repo/utils`** so the main worker and the research worker share one source (avoid drift).
   - Generate via OpenRouter (existing `generate-image` image path / `openrouter-image-generation`), upload to the same stable R2 key, then set `services.image_url` (service) or `hero_image_url`/`logo_url` + lock (hero/logo). A dev-regenerated visual is custom → locked.
   - Bust KV.

4. **`POST /:shopId/remove-image`** (**new, developer-only**) — body `{ type }`, `type = hero|logo|service:<serviceId>`.
   - `service:<id>` → `UPDATE services SET image_url = NULL …` → the card reverts to the AI catalog pool image, or the imageless placeholder if the pool has none (the site already handles imageless cards).
   - `hero` / `logo` → clear the URL (`NULL`) and remove the key from `locked_images_json`.
   - Bust KV. (R2 objects may be left as harmless orphans.)

Web proxy routes (`apps/web/app/routes/api.shops.$shopId.*`): `upload-image`, `save-image`, `generate-image` already exist as resource routes and forward the body verbatim (so the extended `type` passes through unchanged). **Add** `api.shops.$shopId.remove-image.tsx` (resource route, matching the invariant that all `api.*` routes are resource routes).

### Public render — service image resolution

The public site's primary service path is `mapApiServicesToCommercial(apiRows, catalog)` in `apps/web/app/routes/$shopSlug.tsx`, fed by `GET /api/shops/:slug/services`. Changes:

- Add `image_url` to the public services API response (`apps/worker/src/routes/services.ts`, from the `getServicesByShop` row via `SELECT *`) and to the `ApiPublicService` type.
- `mapApiServicesToCommercial` resolves `image_url: row.image_url || catalog[index] || ""` — custom wins, else the positional AI pool, else imageless.
- `normalizeCommercialServices` (the `services_json` fallback path) already honours `raw.image_url ?? catalog[index]`; leave as-is.

Ordering note: `catalog[index]` alignment holds because both the catalog and the service list resolve through `getServicesByShop` (`ORDER BY category, name`); custom `image_url` is keyed by service ID and is independent of that ordering.

### Regenerate interaction (stickiness)

- **Per-service:** `services.image_url` lives on the `services` table, which the regenerate pipeline (research → images → builder) never writes. So per-service customs **survive automatically**, and the site prefers them over the freshly generated catalog pool.
- **Hero / logo:** in the assembler (`apps/workers/builder/src/index.ts`), before the `shop_sites` UPDATE, read the existing row's `hero_image_url`, `logo_url`, `locked_images_json`. For a locked slot, bind the **existing** value instead of the newly generated `images.heroUrl` / `images.logoUrl`. The INSERT-when-no-row path is unaffected (no existing row ⇒ nothing locked).
- Orthogonal to the existing `skip_images` regenerate flag (which reuses all images); locks are finer-grained.
- *Secondary optimisation (non-goal for MVP):* skip AI-generating images for locked visuals to save cost — requires threading lock state into research/images; wasted generation is accepted for now.

### Frontend — shared `VisualManager`

One shared component (`apps/web/app/components/VisualManager.tsx`) rendered in both dashboards.

- **Props:** `shopId`, `apiUrl`, `role: "developer" | "admin"`, and the visuals data (logo url, hero url, `services: {id, name, image_url}[]`, the catalog pool for fallback preview, and hero/logo lock state).
- **Layout:** a responsive grid of tiles — Logo, Hero, then one tile per service (labelled by service name). Each tile shows the current image or a placeholder, a "custom" badge when locked, and role-gated actions:
  - admin → **Upload**.
  - developer → **Upload**, **Regenerate**, **Remove**.
- **Flows:**
  - Upload: hidden file input → `POST upload-image` (multipart, `type`) → `{imageUrl}` → `POST save-image` (`type`, `imageUrl`) → revalidate. Reuse/generalise the existing hero/logo upload UI in `dev.shops.$shopId._index.tsx` ("Brand images").
  - Regenerate (dev): `POST generate-image` (`type`) → revalidate; show a spinner.
  - Remove (dev): `POST remove-image` (`type`) → revalidate.
- **Placement:**
  - Dev hub: replace the existing "Brand images" (hero/logo) block in `dev.shops.$shopId._index.tsx` with `<VisualManager role="developer" … />` (now covering services too).
  - Admin dashboard: a new "Visuals" section/route in the admin area (`admin.*`), using `<VisualManager role="admin" … />` with the admin's own `shop_id`.

### Auth & roles

- Upload + save: developer or admin-of-shop.
- Regenerate + remove: developer only (403 for admin) — enforced server-side, not just hidden in the UI.
- All service-scoped operations validate `service.shop_id === shop.id`.

## Error handling & edge cases

- Upload: reject non-png/jpg/webp and > 5 MB (existing checks).
- `service:<id>` not found or not in shop → 404/403.
- Admin attempting regenerate/remove → 403.
- KV `site:<slug>` busted on every mutation so the public site updates immediately.
- Soft-deleted service (`is_active = 0`) keeps its `image_url`; harmless.
- Removing a service's custom image with no catalog-pool image → imageless card (already handled).
- Re-upload overwrites the stable R2 key; a deleted service leaves an orphan R2 object (acceptable).

## Testing

- **Worker (vitest-pool-workers):** upload/save/generate/remove for `service:<id>`; role enforcement (admin upload OK; admin regenerate/remove → 403); service-ownership; `save-image` writes `services.image_url`; hero/logo save sets `locked_images_json`; assembler preserves a locked hero/logo on regenerate and a per-service custom survives; migration chain replays with 045.
- **Web (vitest/jsdom):** `VisualManager` renders role-gated actions and the custom badge; the upload flow calls upload-image then save-image with the right `type`.

## Rollout / deploy

- **Migration 045** + main-worker endpoint changes + `services.image_url` in the public API + web (`VisualManager`, `$shopSlug.tsx`, proxy route) all ship via CI on push to `main` (CI runs the migration on main-worker deploy).
- **`services.image_url`** reflected in `schema.sql`; `shop_sites.locked_images_json` is migration-only (not in `schema.sql`).
- **Assembler (`apps/workers/builder`)** lock-preservation change is a **manual `wrangler deploy`** (background worker, not CI). Per-service stickiness needs no worker deploy.
- No change required to the research or images workers for the MVP.

## Decisions resolved

| Question | Decision |
|---|---|
| Where / who | Both dev hub and shop-admin dashboard, shared component, role-aware |
| Actions | Owner: upload only. Developer: upload + regenerate-one + remove |
| Regenerate behaviour | Preserve custom (locked) images; regenerate only still-AI visuals |
| Storage | Approach 1: `services.image_url` (service-keyed) + `shop_sites.locked_images_json` |
