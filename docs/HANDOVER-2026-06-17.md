## Site generation — how it works now (read before touching it)

Flow (all async via Cloudflare Queues):

```
Dev panel "Generate Website →"  (apps/web/app/routes/dev.shops.tsx, expanded-shop panel)
  → POST /api/shops/:shopId/generate-site   (apps/worker/src/routes/shops.ts)
      → site_research_queue
          → research worker   (apps/workers/research/src/index.ts)  — AI builds the spec (palette, copy, image prompts, legal)
              → text worker   (apps/workers/text/src/index.ts)      — AI writes the site copy
                  → builder/assembler (apps/workers/builder/src/index.ts) — writes the `shop_sites` row in D1
```

**Palette override path (PR #27/#28):** the dev panel sends `color_primary`/`color_accent` only
if the user picked a palette. `shops.ts` forwards a *validated 6-hex pair* into the queue payload.
The research worker carries it through KV + overwrites `spec.palette`; the text worker re-applies
it **last** (so it beats the text model's own colour pick); the builder writes it to BOTH
`color_primary` and the winning `owner_color_*` columns. The public site API reads
`owner_color_primary || color_primary` ([shops.ts](../apps/worker/src/routes/shops.ts) ~L554).

**Robustness fix (PR #30, `apps/workers/research/src/index.ts`):** previously the research worker
called the AI once and hard-rejected the whole spec on any non-deterministic deviation (wrong
catalog count, `trust_signals`/USPs ≠ 3, or an empty `{}` response), with no retry → intermittent
"invalid JSON" failures. Now it: surfaces empty responses, validates structure only (counts are
**coerced**, not rejected, via `coerceSpecCounts`), and **retries up to 3×**, logging the raw
response on each failure.

## ⚠️ Critical operational gotchas

1. **Background workers are NOT deployed by CI.** `apps/workers/{research,text,builder,images,
   chatbot,audit,booking}` deploy **manually only** — `cd apps/workers/<name> && npx wrangler deploy`
   (prod is the default env; no `--env`). A merge to `main` only auto-deploys `apps/web` (Pages) and
   `apps/worker` (the main Hono API). **If you change a background worker, you must deploy it by hand.**
   Current live versions deployed this session: research `fdfebfb5`, text `9e034437`,
   builder/assembler `3b8dc437`. Partial deploys are graceful (old workers ignore unknown queue fields).
2. **Prod is gated.** Wrangler is OAuth-logged-in as `bmorris0565@gmail.com`. Prod merges, prod D1
   queries (`wrangler d1 execute pivot-parlor-db --remote`), and manual worker deploys all require
   explicit human authorization in the agent harness. `wrangler d1` may throw a transient `7403`
   on the first call — retry, it succeeds.
3. **Reading job status:** to debug generation, read the `generation_jobs` table directly
   (`status` / `stage` / `error` / `created_at` vs `updated_at`). `wrangler tail <worker>` is
   unreliable on this Windows box (the process drops after ~2–3 min) — don't depend on it.
4. **`.js` twins shadow `.tsx` routes** in `apps/web/app/routes/` (Remix discovery prefers `.js`).
   After editing a `.tsx` route, remove the stale `.js` twin. They're gitignored; `npm run build`
   regenerates/cleans them.
5. **graphify on Windows:** the knowledge graph lives in `graphify-out/` (gitignored). Run
   `/graphify update` from `pivot-parlor/`. If detection reports everything "deleted", the persisted
   scan root must be a native Windows path (`F:/Projects/Pivot Parlor/pivot-parlor`, not `/f/...`) —
   the native Windows Python can't resolve MSYS-style paths.
6. **Do not re-run** `cleanup-legacy-prod.sql` or `migrate.mjs --baseline` (both already applied to
   prod; re-running is destructive/wrong). See the 06-14 handover.
