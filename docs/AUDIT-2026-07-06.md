# Pivot Parlor — Whole-Codebase Audit (2026-07-06)

Audited against four stated product goals:

1. **Industrial-grade multi-tenant** barbershop + beauty-salon SaaS.
2. **Inventory + point-of-sale** of barbershop/beauty retail items.
3. The **most advanced booking + payment** system.
4. **No two shops look alike** (per-shop generated sites).

> **Method note.** This pass combined a direct read of the code with parallel review agents. Four of the review agents (booking, data-layer, frontend, ops) returned empty — they made zero tool calls and emitted unrelated boilerplate instead of findings — so those dimensions were audited directly instead; their empty output was discarded and not acted on. The security and payments agents returned full, verified reports and are folded in below. Every finding here is anchored to `file:line` evidence in the current tree.

---

## 1. Verdict scorecard

| Goal | State today | Grade |
|------|-------------|-------|
| **Industrial-grade multi-tenant** | Tenant isolation + auth are genuinely solid (SEC-1/SEC-2 fixed, role-aware `requireShopRole`). Undermined by: money-as-float, single shared D1 with no DR story, **no error observability**, and an opt-in-only CI gate. | **C+ / partial** |
| **Inventory + sales of items** | Effectively **not built**. No product catalogue, SKU, stock, supplier, or POS tables. The only "product" trace is free-text line items in an unused checkout. | **F / absent** |
| **Most advanced booking + payment** | Live booking works but is **basic and takes no payment**. The advanced Stripe-Connect deposit/checkout engine exists in `apps/workers/booking` but is **un-wired and non-functional** (no Connect onboarding, not called by the site). | **D / two half-systems** |
| **No shop looks alike** | **Not met — worse than templated.** *Every* shop renders through a **single** live layout (`CommercialTemplate`) with an identical section order; the 6 named templates are **dead code**, and ~40% of each page is byte-identical hardcoded copy. Rich per-shop design intent is generated then discarded. | **D- / one layout for all** |

**One-line summary:** the multi-tenant *foundation* (auth, isolation, migrations, the free booking path, AI copy/imagery) is well-built and well-tested; but the three things that define the product's ambition — **payments that actually move money, a retail/inventory business, and genuinely unique sites** — are each either missing, orphaned, or superficial.

## 3. What is already good (do not regress)

- **Critical auth hole is closed.** `/auth/register` now clamps non-developer callers to `role=customer, shop_id=null` (`apps/worker/src/routes/auth.ts:149-159`), regression-tested (`auth.register-privilege.test.ts`, `auth.shop-role-gating.test.ts`). Prior **SEC-1/SEC-2 fixed.**
- **Tenant isolation is coherent.** One role-aware primitive `requireShopRole()` gates by role **and** `shop_id` (`apps/worker/src/middleware/rbac.ts:52-68`); child resources re-scope to the shop (404 on mismatch); IDOR tests exist (`sweep.idor`, `schedule.idor`, `waitlist.idor`). Prior "staff can PATCH shop" (ARCH-1) fixed — `shops.ts:1282` is admin-only.
- **Public booking is correctly validated.** Off-hours/misaligned times are rejected against real availability (`apps/worker/src/routes/bookings.ts:157-168`) with a unique-active-slot index as the race backstop (migration `018`). Prior **E2E-1 fixed.**
- **Onboarding payment is production-grade.** Official Stripe SDK, hosted Checkout, raw-body signature-verified webhook, card data never touched server-side (SAQ-A eligible), now unit-tested (`webhook-checkout.test.ts`).
- **Migration discipline** — tracked `schema_migrations`, baseline mode, replayable chain (`scripts/migrate.mjs`).
- **AI does not emit raw HTML** — it returns structured JSON rendered by React templates, so the generated sites are not an XSS vector.
- Prior **ABUSE-5 (SQL LIMIT/OFFSET interpolation) fixed** — now parameterised (`queries.ts:828-844`).

### B. Booking system — *two divergent systems; live one is basic*

The most important architectural fact in the repo: **there are two booking systems writing to the same `bookings` table.**

- **Path A (LIVE): main worker.** The customer site posts to `/api/bookings` (`apps/web/app/routes/$shopSlug.book.tsx:59`). Slots are computed dynamically from `schedules`; **no deposit or payment is taken**; status is `pending`; races are guarded by the unique-slot index. Solid but minimal.
- **Path B (ORPHANED): `apps/workers/booking`.** A materialised `bw_availability` slot table, Stripe-Connect deposits, tips, ad-hoc products, QR check-in, and a checkout/commission ledger. **The web app never calls it** (only a dev constants file references it), there is **no service binding** from the main worker, and it requires a Connect account that nothing provisions.

| Sev | Finding | Evidence | Fix |
|-----|---------|----------|-----|
| **High** | **Dual booking systems / orphaned advanced engine.** Divergent availability models (dynamic `schedules` vs materialised `bw_availability`) and duplicated walk-in/checkout logic against one shared `bookings` table. The advanced engine is un-integrated WIP. | `apps/worker/src/routes/bookings.ts` vs `apps/workers/booking/src/routes/bookings.ts`; `$shopSlug.book.tsx:59` | Choose one. Recommend promoting Path B (it has the payment/POS features) *or* folding deposits into Path A; delete the loser. This decision precedes P1-4. |
| **Med** | **Materialised `bw_availability` scaling.** Pre-generating a row per staff × slot × day grows unboundedly and needs a generator/janitor; the dynamic `schedules` model does not. Choose deliberately. | `apps/workers/booking/src/db/ensure-schema.ts:54`; `routes/setup.ts` | If keeping Path B, add slot-generation + retention jobs and indexes. |
| **Med** | **Reminder queue reliability.** Reminders use `delaySeconds` capped at 12h re-delayed across retry "hops" with `max_retries=10` (`apps/worker/wrangler.toml:36-38`). A genuine failure consumes the same budget as scheduling, so a far-future booking can exhaust hops or a transient error can drop the reminder. | `apps/worker/src/services/reminder.ts`; `wrangler.toml` | Separate scheduling from failure-retry (e.g. a cron sweep over due reminders instead of long delay chains). |

**Missing for "most advanced" booking (none implemented):** buffer/turnaround between appointments, per-service/ per-shop deposit + cancellation-window policy actually enforced, no-show handling that charges, recurring & group/party bookings, multi-service and multi-staff baskets, resource/chair/room allocation, customer self-reschedule, calendar sync (Google/iCal), waitlist auto-promotion, dynamic/peak pricing, memberships/packages.

### D. Inventory & POS — *the entire subsystem is missing (Goal #2)*

Confirmed absent: no `products`, `stock`, `sku`, `suppliers`, `purchase_orders`, `sales`, or catalogue tables anywhere in `schema.sql`, the 21 migrations, `queries.ts`, or the web routes. `shop_settings.sells_products` and a `services.service_type='product'` hack exist, and the orphaned checkout accepts **free-text** `{name, price, quantity}` line items (`apps/workers/booking/src/routes/bookings.ts:99-112`) — untracked, no stock, no catalogue. There is **no way to define a product, hold stock, sell at a counter, or report COGS.**

**Key structural facts (verified):**
- The PRD explicitly scoped inventory/POS as a **Phase-2+ non-goal** (`docs/PRD.md:43,96`; `docs/STRATEGY.md:237` lists "Product retail sales (inventory + POS)" as an unbuilt item) — a deliberate gap to fill now, not a regression.
- The orphaned checkout's line items require `booking_id NOT NULL` (migration `019`), so a **standalone counter/retail sale is structurally impossible** today — retail can only hang off an appointment.
- `bw_commission_ledger` records `services_amount` only, so **retail commission and staff attribution are unmodelled**.
- `shops` has no `currency` column (although `packages/types` `Shop.currency` implies one) — add `currency TEXT NOT NULL DEFAULT 'GBP'`.

**Design principle — one commerce spine, do not fork the ledger.** Build POS *through* the existing money/commission ledgers, not beside them: reuse `bw_transactions` (tender) and `bw_commission_ledger` (commission, extended with a `retail_amount`/`staff_id` path), and replace the structurally-blocked `bw_booking_items` with a unified `sale_line_items` that both appointment-checkout and counter-POS write through (a `sales` header with a **nullable** `booking_id`). This also resolves the duplicate-checkout problem in §B. Add **back-bar consumption** via a `service_products` bill-of-materials that emits negative `consumption` stock movements when a service completes. All DDL lands in main-worker migrations `022+` (canonical owner), never a background-worker `ensure-schema`.

**Recommended schema** (follows repo conventions: TEXT uuid PKs, `shop_id` FK `ON DELETE CASCADE`, **integer pence** for money, `created_at TEXT`):

```
product_categories(id, shop_id, name, sort_order, is_active)
suppliers(id, shop_id, name, email, phone, notes, is_active, created_at)
products(
  id, shop_id, category_id→product_categories, supplier_id→suppliers,
  name, description, brand, sku, barcode,          -- UNIQUE(shop_id, sku)
  cost_price_pence INT, retail_price_pence INT, tax_rate_bps INT,
  is_professional INT,   -- back-bar / not for retail sale
  track_stock INT, image_url, is_active, created_at)
product_variants(id, product_id, shop_id, name, sku, barcode,
  cost_price_pence INT, retail_price_pence INT, attributes_json)
stock_levels(id, shop_id, product_id, variant_id, quantity INT,
  reorder_point INT, reorder_qty INT)             -- UNIQUE(shop_id, product_id, variant_id)
stock_movements(id, shop_id, product_id, variant_id,
  type,   -- receive|sale|adjustment|waste|transfer|return
  quantity_delta INT, unit_cost_pence INT,
  reference_type, reference_id, staff_id, note, created_at)
purchase_orders(id, shop_id, supplier_id, status, ordered_at, received_at, total_pence INT)
purchase_order_items(id, po_id, shop_id, product_id, variant_id, quantity INT, unit_cost_pence INT)
sales(id, shop_id, booking_id?, customer_email?, staff_id,
  subtotal_pence INT, discount_pence INT, tax_pence INT, tip_pence INT, total_pence INT,
  tender_type, stripe_payment_intent_id, status, created_at)
sale_items(id, sale_id, shop_id, item_type,  -- service|product
  product_id?, service_id?, name, quantity INT,
  unit_price_pence INT, cost_price_pence INT,  -- COGS snapshot
  tax_pence INT, line_total_pence INT, staff_id, is_commissionable INT)
```

Reuse the existing `shop_id` tenancy, the commission model, and Stripe plumbing. Index every table on `shop_id` (+ `sku`, `barcode`, `sale.created_at`).

**Phased build:** (1) catalogue + manual stock movements + low-stock view; (2) counter sale/POS — cart mixing services + products, discounts, tips, Stripe payment, receipts; (3) suppliers + purchase orders + back-bar consumption (auto-deduct product usage when a service completes) + reporting (COGS, margin, sell-through, per-staff retail); (4) barcode scanning, multi-location, stock takes, returns/exchanges. Unify this "sale" with the booking checkout so a single transaction can contain services **and** products — which also resolves the duplicate-checkout problem in §B.

### F. Site uniqueness — *not met; worse than "a few templates" (Goal #4)*

The live render path is a **single** component, `CommercialTemplate`, used for **every** shop with a fixed section order (hero → trust bar → services → about + pillars → team → how-it-works → reviews → location → final CTA) — `apps/web/app/routes/$shopSlug._index.tsx:110`; `apps/web/app/components/CommercialTemplate.tsx`. The six named templates (`Minimal/Luxury/Vibrant/Editorial/Classic/Fresh`) and the `services/site-generator.ts` that selects them are **dead code — imported by nothing** on the render path (so my earlier "6 templates" read was of a legacy path, not the live one). Real per-shop variation is genuine but shallow: one accent colour, two Google fonts, hero/service imagery, and headline/about copy. Most damning: the generation pipeline **already computes** rich per-shop design intent (a 5-colour palette, `layout_mood`, `brand_voice`, `subheadline`, `hero_cta`, three `trust_signals`, three `unique_selling_points`) and then **throws almost all of it away** before it reaches the page.

1. **Stop discarding the spec (M, highest ROI):** persist and serve `layout_mood`, `brand_voice`, `trust_signals`, `usps`, `hero_cta`, `about_title` and the full palette; replace the hardcoded pillars/steps/CTA/hero-subline with them. Converts ~40% of each page from identical to per-shop at no new AI cost.
2. **Layout archetypes on `layout_mood` (M):** make `CommercialTemplate` an archetype dispatcher varying hero style, service-card treatment, and section order/density.
3. **Real colour range + contrast guard (M):** adopt the 5-colour palette as tokens, drop forced `text-white`, compute AA-safe foregrounds → unlock light/warm shops.
4. **Design tokens seeded by `shopId` (M):** derive radii/borders/shadow/spacing from palette + mood, deterministic per shop (stable re-render, combinatorially unique).
5. **Curated typography (S–M):** honour `heading_weight`/`heading_style`; self-host fonts (also fixes LEG-5).
6. **Optional AI-authored layout (L):** emit a **validated JSON block list** from a fixed block library (never HTML), schema-validated and composed server-side.

The stability fix in commit `e57ebb9` (retries + schema validation across research/text/builder) made the 4-worker/3-queue pipeline resilient, but that fragility is itself a symptom that the generation architecture is more complex than the output justifies.
