# Showcase harness

Runs the real site-generation pipeline locally for the two fictional portfolio
shops, publishes them, and verifies the result through the public API. Nothing
here touches a Cloudflare account, production data or a paid API.

```bash
node tools/showcase/run.mjs                 # bundle, migrate, seed, generate, verify, exit
node tools/showcase/run.mjs --serve         # ...then keep the API on :8787
node tools/showcase/run.mjs --serve --skip-build   # reuse the last worker bundles
node tools/showcase/run.mjs --serve --pending-review  # ...and leave the salon's next
                                                      # version waiting for review

# in a second shell, the web app against it:
cd apps/web && npm run build
npx wrangler pages dev ./build/client --port 8788 --binding API_URL=http://127.0.0.1:8787
# open http://127.0.0.1:8788/ferdyms-barber-shop-demo
#      http://127.0.0.1:8788/linden-and-lark-demo
#      http://127.0.0.1:8788/ferdyms-barber-shop-014   (the original demo URL, an alias)
```

The run exits non-zero unless both shops verify, every demo write probe is
refused, and no booking, waitlist or walk-in row exists for a demo shop. It
then regenerates the barber shop while it is live and checks the owner review
step end to end: the job finishes as "candidate", the public site and its row
are unchanged, the pending version is previewable, publishing a different
version is refused (409), and Publish writes the row, clears the pending
version and the shop still verifies. The report is written to
`.state/report.json`.

## What is real

- The six production workers (API, booking, research, text, images,
  assembler), bundled by `wrangler deploy --dry-run` from this checkout.
- A fresh database built by the real migration runner
  (`scripts/migrate.mjs --persist-to`).
- Owner setup through the public API: settings (address, phone, hours),
  services, team members with specialities, portrait uploads, AI settings.
- `POST /generate-site`, the queues between the workers, research validation
  and coercion, the text worker's menu-from-source rule, the assembler's
  truthfulness gate and no-downgrade image merge, `POST /activate`, and the
  public read endpoints the web app renders from.
- Probes that try to book, join the waitlist and join the walk-in queue on
  each demo shop (all must return 403).

Only the shop rows themselves are inserted directly, as the E2E fixture does:
the platform's create route always mints `<name>-<number>` slugs, so by design
it cannot produce the code-owned demo ids and `-demo` slugs.

## What is replayed (read before quoting any output)

- **The model.** Every outbound request leaves the workers through one handler.
  Research and text calls are answered with the responses in `replay.mjs`.
  Those responses were AUTHORED for this showcase in the shape the prompts ask
  for; a live run sends the same prompts to the configured model and may word
  things differently. The copy states only what the owner records in
  `shops.mjs` contain, plus the owner's style notes.
- **The images.** Image calls are answered with the files in `assets/`. Those
  were generated outside the platform with FLUX.1 [schnell]
  (black-forest-labs, Apache-2.0), 25 through AI Horde and 2 through the
  public Hugging Face Space, from the prompts in `image-prompts.mjs`. They are
  not the platform image model's output. `assets/PROVENANCE.json` records the
  source, seed, prompt and sha256 of each file. Every person shown is
  AI-generated and depicts no real individual. `gen-images.mjs` regenerates a
  file (delete it first).
- **The logo.** The replay refuses the logo prompt, so both sites use the
  typeset shop name. This also exercises the images worker's failure path.
- **Staff portraits** are the owner uploads in the real flow, so here they are
  uploaded through `POST /staff/:id/avatar`, not generated by the pipeline.

Every other outbound request (OpenRouter's model list, email, payments) is
refused and listed in the report.

## The fictional shops

`shops.mjs` holds both shops. Phone numbers come from Ofcom's drama ranges,
which are never allocated to real lines. Addresses carry no street or number,
and the street line reads "Illustrative address". Staff emails use the
reserved `.invalid` domain. A third, ordinary tenant (`control-cuts-901`)
must come out of every check untouched and without demo labelling.
